## التطبيق المحلي والتعريض المصطنع

طُبقت المجموعة الحرفية والسياسات المرجعية على القاعدة المملوكة في معاملة واحدة بعد الفحوص، فأصبحت48 جدولًا وكلها RLS. بقيت حسابات Auth والأدوار والعضويات وoverrides كما كانت، وتطابقت قيم أعمدة البيانات الأصلية؛ إضافة أعمدة default لا توصف بأنها تطابق JSON صفوف كامل. ثبت بقاء ACL جدول/أعمدة stock وتعريف stock_read_safe وأجسام إصلاحات الصلاحيات والمخزون السابقة.

بعدها، في معاملة منفصلة معلنة، أُضيفت متطلبات API المصطنعة: authenticated SELECT للجداول المرجعية/الدفاتر، وSELECT/INSERT/UPDATE/DELETE لجداول مسودات/بنود/مرتجعات البيع والشراء، وUSAGE/SELECT للـsequences الست. كل العمليات تبقى تحت RLS المصدر، بلا anon/PUBLIC table grants أو service-role في العميل أو تعطيل RLS. هذه ليست سياسة إنتاجية مقترحة أو دليلًا بأن كل DML مسموح؛ الفحوص الفعلية للصلاحيات والمعاملات تليها. منح canonical EXECUTE غير الآمنة ظلت دون تصحيح خفي لكي يُختبر أصل المشكلة فعليًا.

## نتائج Auth/API السابقة للإصلاح

استخدمت Supabase SDK الحقيقية وAuth/PostgREST على loopback، بلا mocks.12 طلب HTTP تضمنت دخول الحساب المحدود وخروجه المحلي وقراءة رفض الخزنة و9 طلبات RPC. سجل النتيجة `OBSERVED_SECURITY_BYPASS` وليسPASS أمان؛ الملاحظات الخمس:

- anonymous وauthenticated المحدود استدعيا reserve_stock مباشرة فزاد الحجز1، ثم unreserve_stock أعاده، دون صلاحية تشغيل مناسبة.
- طلب anonymous إلى confirm_sales_order معp_user_id الخاص بالمدير غيّر مسودة مصطنعة محفوظة إلىconfirmed وحجز1. إعادة الطلب لم تضاعف الحجز؛ cancel_sales_order من الطلب المجهول أعاده. هذا وصف سلوك retry فقط، وليس قبول هوية caller أو اعتماد دورة بيع كاملة.
- الحساب المحدود أضاف حركة خزنة1 من add_vault_transaction ونسبها للمدير رغم أن SELECT الخزنة له أعاد صفر صفوف؛ طلب anonymous أضاف حركة أخرى1. لا فحص helper-idempotence مصطنع؛ العقود الذرية وإعادة المحاولة للعملية المالكة لم تُؤهل بعد.

أنشئت مسودة وخزنة فقط لهذه التجربة، ثم أُزيلتا وبنودهما/حركاتهما وأُعيدت كمية/حجز/تكلفة المخزون وupdated_at الأصلي. تطابقت أعداد وبصمات بيانات كل الجداول العامة48 قبل التجربة وبعدها، واختتمت جلسة الدخول المحلية وأُغلقت قنوات/auto-refresh العميل. Auth يسجل metadata الدخول المعتادة؛ لا ندعي تطابق كل مخطط Auth بعد login أو محو سجله. لا بيانات إنتاج أو استنتاج عن تعرض الموقع المنشور فُحص هنا.

## الخطوة التالية وحد القبول

1. بوابة أمان أمامية مستقلة من المخالفات المثبتة: ضبط الوصول إلى helpers الداخلية وإلى RPC الأعمال حسب caller الحقيقي، مع حفظ استدعاءات الدوال المالكة ومسارات الواجهة المشروعة ومراجعة Claude. لا تعديل معاني مالية أو إدخال dedup عام للـhelpers.
2. تكرار نفس طلبات المخالفة كاختبارات رفض بعد الإصلاح، وإثبات أن العمليات المصرح بها ما زالت تنجح. ثم مسارات حفظ البيع/الشراء والمرتجعات/العكس والفشل الذري وإعادة محاولة RPC، عبر خدمات ومتصفح التطبيق الحقيقيين، مع الرصيد والكمية/WAC والقيد المتوازن.
3. استعادة البيئة بعد العمليات، وتأهيل App/الحقول/overlays والأداء/التحديث وRealtime والفحص الموحد على SHA النهائي قبل تسليم المرشح.
