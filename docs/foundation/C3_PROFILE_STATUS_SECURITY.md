# حالة الحساب وحارس المسارات — C3

## الخلل والإصلاح المحدود

على المصدر الأب `996d4e13a834ef3d890968fcad4b97d78a3e295b`، نجح إخراج الحساب غير النشط أو الموقوف من الواجهة، لكن الجلسة القديمة ظلت تقرأ العملاء مباشرة. الاختبار في قاعدة C3 المصطنعة أبقى JWT نفسه: كانت `check_permission` ترجع true والقراءة صفين في حالات active/inactive/suspended ثم active.

التعديل الأمامي `20261011040000_active_profile_permission_gate.sql` يشترط ملفًا active قبل **كامل** تعبير الصلاحية، بما يشمل المنح الفردي والدور. بقيت أولوية المنع الفردي، انتهاء override، wildcard والدور النشط كما كانت. نفس التوقيع وSQL/STABLE/SECURITY DEFINER؛ المالك وACL محفوظان، والعلاقات مؤهلة مع search_path فارغ. لا تغيير في migrations التاريخية أو سياسة الملف الذاتي أو كود الواجهة.

هذا يغلق صلاحيات تستعمل الدالة؛ لا يعني إبطال JWT نفسه أو منع جميع API. سياسات الملف الذاتي تسمح باكتشاف الحالة لكي يخرج التطبيق الحساب. مسارات لا تستعمل `check_permission`، والمعاملات الطويلة وRealtime، تحتاج تأهيلها المستقل.

## الأدلة المحلية

- `C3_GUARD_AUTH_RUNTIME_EVIDENCE.json`: ثماني حالات/26 طلبًا حقيقيًا لمكوّني AuthProvider وProtectedRoute الأصليين: المجهول، سماح العملاء/منع المالية، منع فوق wildcard، حساب بلا دور مع منح فردي ثم انتهاء المنح، inactive وsuspended، واستعادة الحساب. تركيب Routes اختباري؛ ليس App كاملًا أو صفحات الأعمال. لا محاكاة SDK أو خدمات أو استجابات HTTP. بصمات ملفات المصدر السبعة ثابتة، والمتصفح والخادم أُغلقا.
- `C3_PROFILE_STATUS_RUNTIME_EVIDENCE.json`: 14 طلب Auth/REST حقيقيًا، قبل الإصلاح وبعده. الحساب النشط يقرأ صفين؛ inactive/suspended يقرآن صفرًا بعد الإصلاح بنفس JWT؛ العودة إلى active تستعيد الصفين. إعادة تفعيل الحساب لنفسه رفضت 403/42501 في الحالتين قبل/بعد. 13 حالة SQL تشمل المنح الفردي مع التعطيل وبلا دور، expiry، wildcard والمنع، الدور المعطّل والهوية الغائبة. نجح إعادة التطبيق مع تطابق تعريف الدالة والمالك/ACL، واستعادة التعريف الأصلي ثم إعادة تطبيق الإصلاح. بصمات حالات الملفات والأدوار والمنح والمخزون عادت كما كانت؛ بقي الإصلاح المحلي المؤهّل.
- `supabase/tests/active_profile_permission_gate.sql`: اختبار رجعي محفوظ يستعمل الدالة والمخطط الحقيقيين، وينشئ سجلات مصطنعة داخل transaction ثم ROLLBACK. التنفيذ المحلي مع ON_ERROR_STOP نجح؛ لا mocks أو تعطيل RLS.
- `C3_PROFILE_STATUS_PLAN_EVIDENCE.json`: EXPLAIN ANALYZE تحت دور authenticated وRLS الفعلي؛ ثلاث InitPlans كل منها نُفّذت مرة واحدة، وصفان. زمن التنفيذ 2.552ms والتخطيط 0.592ms لعينة صغيرة واحدة، وليس قياس إنتاج أو مقارنة قبل/بعد أو p95.

## تصحيحات بيئة الاختبار

الاستخراج المحلي الأول أغفل trigger الموجود أصلًا في `02f_hotfixes.sql` لمنع تغيير الحالة الذاتية. قبل التأهيل الجديد استُخرج تعريف الدالة والـtrigger القانوني دون تعديل وطُبق على منصة C3 فقط؛ بصمات المصدر والعبارة في تقرير الأدلة. لم نضف trigger إنتاجيًا منافسًا. نتيجة قراءة العملاء مع تعطيل الحالة لا تعتمد على هذا النقص: تغيير الحالة أجراه postgres، ولم يحاول probe الأول التفعيل الذاتي.

probe الاستكشاف الأول توقع صفًا واحدًا بينما قرأ صفين، فوسم FAIL بعد تسجيل الحالات الأربع؛ أعاد الحالة والخروج. التأهيل الجديد يستخدم شرط قراءة إيجابية ومساواة قبل/بعد الاستعادة، ويثبت الصفر بعد الإصلاح. لا نعتمد على التقرير الأول كاختبار ناجح. حارس المتصفح احتاج تصحيح مولّد المدخل الاختباري بعد فشل أول بلا طلب API؛ التنفيذ المصحح وحده مصدر الثماني حالات.

مراجعة تصميم Claude المباشرة `0a3110f1-0b14-4d55-a48e-97fa8bba825c` انتهت GO مشروطًا بوضع gate فوق المنح والدور وإضافة حالة منح فردي مع التعطيل؛ الشرطان منفذان ومختبران. بلغ الاستدعاء الأول حد turns، ثم استئناف محدود واحد أعطى القرار دون تغيير ملفات.

مراجعة التنفيذ والأدلة المستقلة `de8bf208-3aa1-44e7-b44c-5bc76c718a62`: PASS، exit0، readOnlyViolation=false. المراجع لم ينفّذ الاختبارات أو يعيد حساب البصمات؛ التنفيذ وإعادة حساب بصمات migration ومصدر trigger وملفات الواجهة السبعة أجراها المنسق محليًا. لم يتغيّر ملف إنتاج خلال مراجعة Claude.
