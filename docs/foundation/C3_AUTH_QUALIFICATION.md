# C3 — تأهيل البيئة المحلية وAuth

هذه نتيجة جزئية من الخطة، وليست إغلاق C3 أو اعتماد إصدار للنشر. المصدر الإنتاجي لم يتغير. مشروع الاختبار الجديد `edara-c3-compose-20261011` منفصل عن أي قاعدة موجودة، ببيانات وحسابات مصطنعة فقط.

## البيئة التي تم التحقق منها

أربع خدمات رسمية من عقد `self-hosted/v0.8.2`: PostgreSQL17.6.1.136، GoTrue2.196.0، PostgREST14.17، Envoy1.39.1. Docker29.7.2 وCompose5.5.0. كل الخدمات healthy؛ API على127.0.0.1:59431 وقاعدة البيانات على127.0.0.1:59432، دون نشر Auth/REST منفصلين. شبكة جديدة وvolumes جديدة بعلامة الملكية نفسها؛ لم نعدّل daemon أو stack آخر.

فحصنا ربط المنافذ قبل التشغيل وبعده. Auth health عاد200، واستكشاف REST رفض المفتاح العام403 ونجح بمفتاح الإدارة200 وفق العقد الرسمي. وجود `auth.users` و`auth.uid()` مُثبت؛ قبل SQL التطبيق كانت الحسابات والجداول العامة صفرًا. مفاتيح وكلمات مرور البيئة محفوظة خارج Git ولا تدخل تقارير المراجعة.

مصدر الإعداد الرسمي: [دليل Supabase Docker](https://supabase.com/docs/guides/self-hosting/docker)، و[Compose المثبت](https://github.com/supabase/supabase/blob/self-hosted/v0.8.2/docker/docker-compose.yml). الربط الصريح يتبع [وثائق Docker](https://docs.docker.com/engine/network/port-publishing/). البصمات في `C3_PLATFORM_SOURCE_MANIFEST.json` تحفظ هوية ملفات التهيئة العامة؛ تعديل Compose اقتصر على الخدمات اللازمة والملكية والمنافذ وإيقاف مقدمي الاتصال الخارجي.

## SQL والاختبارات الفعلية

ثماني مجموعات SQL كاملة، مستخرجة بحدود بايت ثابتة وبصمة الملف الكامل، تحفظ Foundation قبل seeds والدوال والسياسات الحالية. `C3_AUTH_STATEMENT_MANIFEST.json` يسجل حدودها وبصماتها. لم نقسّم SQL عند الفاصلة المنقوطة أو نشغّل مجلد migrations كاملًا. نجح تحليل PostgreSQL داخل معاملة ROLLBACK ولم يترك جداول، ثم طُبقت النسخة نفسها. بصمة SQL: `9b975b96433688e8079666e3d3a51a817d50c353f6d6e2e3e76383f906e8f893`.

كل الجداول الثمانية عليها RLS. grants الاختبار منفصلة عن المصدر: SELECT للجداول الخمسة الخاصة بالملف والأدوار والصلاحيات، وUPDATE لعمود `last_login_at` فقط للمستخدم المسجل. ليست هذه إثباتًا لصلاحيات الإنتاج الفعلية.

نجح SDK الموجود في المشروع مع Auth وREST الحقيقيين عبر22 طلبًا:

- إنشاء حسابين مؤكدين عبر Admin API ثم دخول بكلمة المرور.
- الملف الذاتي، wildcard، المنح والمنع النشط، وانتهاء override.
- رفض RPC الصلاحيات للمجهول ولحساب يحاول فحص حساب آخر، وحجب صفوف الملف الآخر عبر RLS.
- تحديث آخر دخول للحساب نفسه فقط؛ تزوير `user_metadata` لم يوسّع نطاقه.
- الدور غير النشط لا يمنح صلاحياته، بينما المنح الفردي النشط يبقى.
- refresh وgetUser وخروج فعلي وتقاعد الجلسة.

هذه ليست استجابات HTTP مصطنعة أو JWT وهمية. التقارير خارج المستودع في مجلد `edara-baseline-foundation/completion`؛ ملفات `platform.private.*` و`c3-synthetic-users.private.json` وlogs الخاصة لا تُرفع.

فحص إضافي مع ملف ذاتي ناجح أثبت أكواد الرفض نفسها: `P0001` لمحاولة فحص صلاحيات حساب آخر، و`42501` للمجهول وبعد الخروج؛ ليست أعطال نقل أو RPC مفقودًا. مراجعة التنفيذ والأدلة المباشرة `c964ad93-81c0-47ab-9bac-efcc4852c27f`: PASS/readOnlyViolation=false. نسخة الأدلة المنقحة محفوظة في `C3_AUTH_RUNTIME_EVIDENCE.json` دون ترويسات أو توكنات أو بيانات دخول.

## ما زال مفتوحًا

مسار `loadSession` وAuthProvider والمتصفح مع الخلفية الحقيقية؛ جداول ومؤشرات dashboard ونطاق المخازن؛ تدفقات المال والمخزون المحفوظة والتصحيح/العكس واستعادة البيئة؛ ودمج DS2 واعتماد SHA النهائي. لا نستنتج مقارنة أداء إنتاجي من هذه البيانات الصغيرة.

مراجعة Claude للإعداد صححت افتراضه الأول بشأن POSTGRES_USER بعد فحص الصورة المحددة: القيمة الموروثة `supabase_admin`. أول create توقف بسبب صيغة مسار Docker Desktop ثم تقاعد؛ الفحص صار قائمة ملفات دقيقة للصيغتين. أول تشغيل بلغ أربع خدمات healthy لكنه توقف عند توقع غير صحيح لاستكشاف REST بالمفتاح العام؛ صُحح التوقع دون تغيير السياسة، ونجح التشغيل التالي. لا محاولة شبكة افتراضية متكررة أو إعادة تشغيل لبيئة قديمة.

مراجعة SQL المباشرة `5c57fa85-249b-470d-95a7-d0eabc22fde6` وافقت على الاستخراج وسجلت فرقًا سابقًا في `66_rls_initplan_safe.sql`: سياسة `roles_delete` تستخدم `auth.roles.update` بدل `auth.roles.delete` الموجودة في Foundation. يلزم اختبار أمني منفصل قبل الحكم أو تعديل الإنتاج؛ لم نخف هذا الفرق داخل bootstrap. فحص `get_low_stock` الأمني ما زال ينتظر توسيع SQL الخاص بالمؤشرات.
