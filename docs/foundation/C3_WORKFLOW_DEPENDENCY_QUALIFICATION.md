# C3 — اعتماد مسارات الحفظ والاستعادة

الأب `69cae84b15a55adc3e0700ee90be2200efb8270c`. هذه دفعة تأهيل اعتماد قاعدة البيانات؛ لا تغيير production أو وظائف التطبيق، ولا قبول مالي كامل. البيئة المملوكة `edara-c3-compose-20261011` تعمل بخدمات PG17/Auth/PostgREST/gateway على loopback. القاعدة الأصلية28 جدولًا عامًا مع RLS وحسابا Auth مصطنعان، وتحتفظ بإصلاحات الصلاحيات النشطة وقراءة المخزون الآمنة السابقة.

## نتائج منفذة

1. أرشيف `pg_dump -Fc` كامل لقاعدة البيئة المحلية، ثم `pg_restore --exit-on-error` إلى قاعدة جديدة من template0 داخل نفس cluster المملوك. تطابقت أعداد وبصمات صفوف الجداول العامة28 وauth.users، وتعريفات الدوال العامة وACL الجداول/الواجهات والسياسات. فحص الأصل بعد الاستعادة أعاد نفس النتائج؛ القاعدة المؤقتة أُزيلت. الدليل `C3_WORKFLOW_PRE_EXTENSION_RESTORE_EVIDENCE.json`، SHA256 الأرشيف `4f190ccb9b103e87d97f7511ea2d76285a456c1b41d4dd4c0a4579993ebb1f25`. الأرشيف الخاص يبقى خارج Git؛ لا يحتوي إلا على البيئة المصطنعة لكنه يتضمن بيانات Auth ولا يُشارك مع Claude.
2. المحاولة الأولى للاستعادة بحساب postgres فشلت عند SET ROLE supabase_admin. تحققنا من أن حساب الإدارة الموجود superuser؛ أُعيدت مرة واحدة في قاعدة مؤقتة جديدة باستخدامه وبنفس الأرشيف، دون تغيير أي دور أو grant. قورنت بصمات الأصل المسجلة قبل المحاولة الأولى، لا snapshot مستحدث يخفي تغييرًا. لا تُعد المحاولة الأولى PASS.
3. على clone جديد من الأرشيف نفسه، نجح إنشاء enum المرتجع والجداول16 الناقصة من SQL المصدر حرفيًا، مع تفعيل RLS داخل معاملة، والتحقق من44 جدولًا دون جدول عام مكشوف، ثم ROLLBACK. عاد clone إلى28 جدولًا/حسابَي Auth، وتطابقت بيانات الجداول الأصلية في clone والأصل مع snapshot. أُزيل clone. الدليل `C3_WORKFLOW_TABLE_DRYRUN_EVIDENCE.json` يحفظ ranges/byte offsets وبصمات المصدر والعبارات؛ SQL المعاملة محفوظ في `supabase/verification/baseline_workflow_tables_dryrun.sql` ببصمة `f82f47610f5f1c172c4cb8e11debf2a643faf147fa698715744aa4a9ca837ec3`.

الجداول الجديدة تشمل بنود البيع والمشتريات والمرتجعات وحركات المخزون والدفاتر والقيود والخزنة والعهدة ووحدات المنتج وشجرة الحسابات. خطوة التركيب تختبر اعتماد FK الأساسي فقط. تفعيل RLS الإضافي إجراء أمان محلي للمعاملة، وليس إثبات استخراج السياسات أو المنح النهائية. لم تُضف grants أو تُكشف هذه الجداول على API ولم تُطبق تغييرات مستمرة على القاعدة الأصلية.

حدود الاستعادة: استعادة قاعدة إلى قاعدة جديدة في نفس cluster تستعمل الأدوار العالمية القائمة. ليست إعادة بناء server مستقل أو استعادة globals، وليست مقارنة تفصيلية لكل كائن أو لكل صف في كل مخطط. فحوص التطابق المباشرة المذكورة أعلاه هي نطاق الإثبات. لم تُجرَ بعد استعادة قاعدة تحمل عمليات البيع/الشراء المحفوظة أو تأهيل SHA النهائي.

## مراجعة العقد واختيار المصدر

جلسة Claude المباشرة `2494a3dc-2d66-430d-8dd2-074748c485ae` انتهت بمراجعة أولى ثم تصحيح واحد؛ كلا التشغيلين exit0/readOnlyViolation=false. الحكم المعدل GO لاستخراج الاعتماد الأحدث، مع إبقاء قبول الإصدار مفتوحًا. اقتراحه الأول استخدام add_vault_transaction من16 بدل113 كان خاطئًا: قراءة الجسم الكامل أثبتت أن16 أيضًا بلا حارس الهوية، واستخدامها يحذف payroll_payment دون حل الخطر. لا يُعتمد ذلك الاقتراح. المرجع هو أحدث جسم113 وقيداه للخزنة/القيد، وأحدث عبارة لكل اعتماد، مع إصلاح أمني مستقل إن أثبت التنفيذ المشكلة؛ لا اختيار نسخة أصغر أسهل في الاختبار.

صححت أيضًا عدد الجداول28 واسم due_date الموجود في04؛ لا حقل credit_due_date مطلوب. RLS لا يمنح table/sequence/function privileges؛ استخراج السياسة واستخراج المنح أو متطلبات التعريض المصطنع خطوتان منفصلتان. inventory الدوال الأولي استكشاف، وليس call graph كاملًا أو SQL جاهزًا للتطبيق. مثال SQL في skills لا ينسخ بدل قواعد المشروع: الأرصدة المخزنة مؤقتًا تتبع triggers المصدر الحالية، ولا توجد إعادة تصميم للدفاتر في هذه الخطة.

## البوابة التالية المحددة

1. إكمال manifest حرفي لدوال البيع/المشتريات/العكس وhelpers وقيودها الأحدث، مع sequences/number triggers وvalidate_sales_item_amounts وcached-balance triggers والسياسات والفهارس والمنح. لا replay شامل للتاريخ، ولا سحب ملف03 كاملًا يعيد جداول موجودة أو يضيف مصروفات غير لازمة. يعاد التحقق من بقية اعتمادات خدمات التطبيق مثل credit RPCs/payment allocation بحسب المسار المختبر.
2. اختبار الاعتماد الكامل داخل clone بمعاملة ROLLBACK، مع حفظ تعريفات الصلاحيات والمخزون السابقة. الدفعة الحالية تثبت طبقة الجدول فقط؛ لا تتجاوز هذه الخطوة.
3. بوابة أمان مستقلة لاستدعاء helpers المحركة للمخزون/الأرصدة مباشرة ولانتحال p_user_id، باستخدام Auth/API الحقيقيين. الجسم الأحدث للدالة المالية بلا حارس، وبعض helpers بلا فحص permission؛ هذه ملاحظات مصدر مادية تحتاج إثباتًا وإصلاحًا أماميًا منفصلًا قبل قبول المرشح. ليست ادعاء تعرض إنتاجي فُحص. فحص retry/idempotence يكون عند RPC العملية التي تملك ذلك العقد؛ لا نفترض أن helper إضافة حركة مالية يجب أن يصبح idempotent من تلقاء نفسه.
4. حفظ بيع draft→confirm→deliver→return، وشراء draft→receive→bill→cancel/return، عبر الخدمات/المتصفح الحقيقيين ببيانات مصطنعة. إثبات الكميات والحجز/WAC والأرصدة والقيد المتوازن، ورفض غير المصرح والفشل الذري وإعادة المحاولة. ثم استعادة الحالة بعد العمليات وتجربة الرجوع والتأهيل الموحد على SHA واحد.

المراجعة النهائية للأدلة والتوثيق في جلسة Claude نفسها: PASS ضمن النطاق، exit0/readOnlyViolation=false. أكدت أن قيود CHECK الأصلية داخل CREATE TABLE هي طبقة تركيب FK فقط؛ القيود الأحدث ليست مطبقة أو مؤهلة في هذه الدفعة. بصمات المصدر ونسخة SQL فُحصت مستقلاً بواسطة Codex؛ لم تُعد مجموعة اختبارات التطبيق لدفعة توثيق/verification SQL دون تغيير production، وبوابة هذه الدفعة هي الاستعادة وdry-run الحقيقيان.

C3 وC5 الشامل وC6/C7 وRealtime ما زالت مفتوحة. نتائج restore/table dry-run لا تغلق العمليات المحفوظة أو بوابة الواجهة أو الأداء أو الإصدار. لا merge/main/DS2 أو نشر أو hosted CI، ولا تغييرات على بيانات إنتاج أو حالات زملاء DS2.
