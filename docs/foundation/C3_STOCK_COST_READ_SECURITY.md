# C3 — حماية تكلفة قراءة أرصدة المخزون

## المشكلة والنطاق
رغم حجب الأعمدة في StockPage، أعادت قراءة stock المباشرة التكلفة لمستخدم يملك inventory.read دون finance.view_costs. سياسة stock_read تعزل الصفوف، لكنها لا تحجب أعمدة التكلفة. حماية get_low_stock السابقة لا تغلق هذا المسار.

هذا الإصلاح محدود بقراءة أرصدة stock: ترحيل20261011030000_stock_cost_read_hardening.sql ومسار getStock العادي. جدول stock ومفاتيحه وعلاقات FK وعمليات الكتابة ودالة get_low_stock واشتراك Realtime لم تتغير. لا إصدار إنتاجي أو قاعدة إنتاج تغيرت.

## العقد
stock_read_safe واجهة قراءة ذات security_barrier، تتحقق صراحة من هوية غير فارغة ومن نفس شرط stock_read: inventory.read_all أو inventory.read مع user_warehouse_ids_set() الذي يجمع إدارة المخزن والعضوية. لأنها تقرأ بحقوق مالكها، لا تعتمد على إعادة تطبيق RLS ضمنيًا. تبقى المفاتيح أعمدة أصلية لتعمل علاقات PostgREST الحالية.

wac وtotal_cost_value يُعادان NULL دون finance.view_costs، والقيم الحقيقية عند السماح. أزيلت كل منح الواجهة للمجهول/PUBLIC/authenticated قبل منح authenticated صلاحية SELECT وحدها. أزيل SELECT على جدول stock نفسه وعلى عمودي التكلفة للمجهول/PUBLIC/authenticated، ثم أُعيد SELECT لثمانية أعمدة غير مالية إلى authenticated. سحب المنح على الأعمدة وحدها لا يكفي مع SELECT على الجدول كله. بقيت منح service_role وحقوق الكتابة والسياسات الأصلية كما هي.

getStock العادي يقرأ الواجهة بدل الجدول، بنفس العلاقات و!inner والبحث والفلاتر والترتيب وrange. أصبح العدّ exact: الدليل السابق أعاد206 بدل4 أو3، و69 بدل2 أو1 عند فلتر المحجوز، و1 لبحث بلا نتائج. لا نغير عددًا صحيحًا إلى تقدير جديد؛ نعيد عدد الصفوف الفعلية بعد الفلاتر والنطاق. اختبار HEAD الرئيسي وقراءة product_id/available_quantity للتحويلات بقي على stock.

## الأدلة المنفذة
- قبل التغيير:26 طلبًا حقيقيًا من client وgetStock الفعليين، وحسابان، و11 تركيب فلتر/صفحة لكل حساب. ثبت تسرب التكلفة للمستخدم المحدود وخطأ العدّ.
- معاملة مؤقتة: نطاق المخازن، حجب التكلفة، رفض SELECT/predicate للتكلفة مباشرة، رفض UPDATE للواجهة، وقيم مالية مسموحة. ROLLBACK أعاد بصمة منح الجدول والأعمدة وغياب الواجهة وأزال override المؤقت.
- تطبيق محلي ثم إعادة تطبيق واحدة: نفس تعريف الواجهة والمنح، SELECT مالي مباشر مرفوض، SELECT غير مالي مسموح، والواجهة للمجهول وللكتابة مرفوضة.
- بعد التغيير:57 طلبًا حقيقيًا عبر Auth/PostgREST وخدمة getStock المحمّلة عبر Vite SSR، دون محاكاة SDK أو HTTP أو service/store. تطابقت الصفوف والعلاقات والترتيب مع القياس السابق في22 حالة، باستثناء NULL للتكلفة دون السماح وتصحيح العدّ. اجتازت فلاتر المخزن/المنتج/البحث/الكميات/المحجوز والصفحات، والمجهول والمحدود وread_all، ومنح/منع/انتهاء finance.view_costs، ورفض تكلفة/predicate/star في الجدول الأساسي حتى للمستخدم المالي، ورفض كتابة الواجهة.
- تجربة UPDATE على stock للمستخدم المالي لم تعدّل صفًا مع RLS الأصلي؛ quantity المحفوظة بقيت10. صف مصطنع إضافي بكمية صفر أثبت فلتر «نفد المخزون»، ثم حُذف.
- أُزيلت كل المنح المصطنعة الإضافية وبقيت الحسابات الأصلية2 والمنح الأصلية4 وأرصدة stock الأصلية4. أُغلق Vite وأوقفت timers/channels وأُعيد fetch؛ مصادر التطبيق لم تتغير أثناء تشغيل الأداة.

بصمات المصدر والترحيل وتقارير الدليل في C3_STOCK_COST_READ_RUNTIME_EVIDENCE.json. مراجعة Claude للعقد انتهت GO بعد استكمال محدود. المراجعة النهائية595d85c4-e9a1-4d1f-938d-9f10ed402209: PASS/exit0/readOnlyViolation=false، دون تغيير مصدر. اجتاز forced TypeScript وlint و17 اختبارًا مركزًا للرئيسية؛ هذه الاختبارات منفصلة عن دليل HTTP الحقيقي. الترحيل والكود دفعة مترابطة: يلزم تطبيق الترحيل قبل ترقية كود القراءة عند اعتماد النشر لاحقًا.

## حدود القبول
هذه بوابة قراءة وخدمة حقيقية، وليست بوابة متصفح/واجهة أو تشغيل مالي كامل. nested base_unit بقي بنفس القيمة السابقة؛ عقد الجداول المصطنع الحالي لا يضم سياسة قراءة units، فلا يثبت هذا الاختبار قبول شاشة الوحدات. لا نسبة تحسن إنتاجية أو p95 مستنتجة من هذه التجربة.

أُغلقت C3-SEC-DIRECT-STOCK-COST في مسار stock المباشر ضمن المرشح المحلي. حماية تكلفة Realtime والمنتجات والحركات والدفعات والتحليلات لم تؤهل بهذا الإصلاح، وتبقى صريحة ضمن C6. التأهيل الشامل للعمليات المحفوظة والاستعادة وApp وتكامل DS2 ومرشح SHA موحد لم يكتمل. لا نشر أو دمج ضمن هذه الدفعة.
