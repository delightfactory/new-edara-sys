# Employee Work Schedules — Final Disposable Rehearsal Runbook

> **وثيقة التنفيذ الوحيدة للبروفة الحالية.**
>
> المرجع التفصيلي لأسماء الملفات وترتيبها هو `CURRENT_MIGRATION_MANIFEST.md`.

## 1. حدود التنفيذ

- الهدف قاعدة Supabase محلية Disposable من نفس مخطط الإنتاج الحالي.
- الإنتاج قراءة فقط.
- لا Branch مدفوع على Supabase، ولا Preview على Vercel.
- الخاصية والجاهزية تظلان `false` طوال البروفة.
- لا جداول لموظفين حقيقيين ولا Backfill للحضور.
- أي اختلاف في مخطط الإنتاج أو Hashes الدوال يوقف البروفة.

## 2. Baseline قبل التطبيق

احفظ قبل M1:

- Migration history.
- تعريفات وACLs دوال الحضور والجزاءات والإجازات والرواتب.
- إعدادات أوقات الشركة.
- وظائف cron الخاصة بالحضور.
- أعداد صفوف الموظفين والحضور والسجلات والجزاءات والإجازات والرواتب والتنبيهات.
- أعداد مسيرات `approved` و`paid` وروابط القيود المحاسبية.

## 3. تطبيق الميجريشنات

طبّق الملفات الـ24 بالترتيب الحرفي الموجود في `CURRENT_MIGRATION_MANIFEST.md`.

بعد كل مرحلة شغّل Verification المقابل قبل الانتقال للمرحلة التالية. الفشل يوقف السلسلة، ولا يتم تخطي الملف أو تعديل قاعدة الاختبار يدويًا لإجباره على النجاح.

## 4. المحاكاة

افتح جلسة Disposable واحدة:

```sql
SET SESSION edara.allow_schedule_simulation = 'disposable-only';
```

ثم شغّل بالترتيب:

1. `20260805200700_hr_employee_work_schedules_final_lifecycle_simulation.sql`
2. `20260805200600_hr_employee_work_schedules_company_and_transition_duration_simulation.sql`
3. `20260805201000_hr_employee_work_schedules_runtime_payroll_simulation.sql`
4. `20260805214500_hr_employee_work_schedules_offday_payroll_simulation.sql`
5. `20260805215200_hr_employee_work_schedules_permission_snapshot_simulation.sql`
6. `20260805215300_hr_employee_work_schedules_zero_day_partial_payroll_simulation.sql`

كل ملف يجب أن يعلن النجاح قبل `ROLLBACK`، وبعده يجب ألا تبقى أي بيانات محاكاة.

## 5. السيناريوهات الملزمة

يجب إثبات الآتي فعليًا:

- أحمد نعمة الله: 6 ساعات يوميًا مع فترتي 15–21 و10–16.
- المبيعات: 9 ساعات يوميًا.
- اختلاف وقت البداية والنهاية مع ثبات مدة اليوم.
- رفض مدة مختلطة داخل نفس النسخة.
- رفض تغيير المدة منتصف الشهر وقبولها يوم 1.
- التأخير بعد فترة السماح نفسها في GPS والتعديل الإداري.
- الإضافي يبدأ بعد نهاية الموظف، ولا ينتج من Auto Checkout.
- الانصراف المبكر يستخدم دقائق التصريح المغطاة فعلًا.
- التصاريح المتداخلة لا تُحسب مرتين في الجزاء المالي.
- حضور يوم الإجازة لا ينتج جزاء أو إضافيًا ولا يعوض غياب يوم عمل.
- فترة استحقاق بلا يوم عمل مقرر تعطي صفر يوم وصفر راتب، لا يومًا وهميًا.
- Snapshot المثبتة لا يمكن تغييرها.
- أي سجل غير مقرر مفتوح يظل مانع مراجعة واضحًا قبل الراتب.
- السلف والعمولات والتعديلات والتأمينات والضرائب والترحيلات لم تتغير.

## 6. الفحص النهائي

بعد رجوع كل المحاكاة ومطابقة عدادات البيانات مع الـBaseline، شغّل فقط:

```text
20260805222000_hr_employee_work_schedules_final_release_preflight.sql
```

الـPreflight القديم الذي يبدأ بـ`20260805200000` لم يعد صالحًا كدليل إصدار بعد إصلاحات المراجعة، ولا يُستخدم.

## 7. مقارنة ما بعد البروفة

يجب أن تتطابق جميع بيانات الأعمال مع الـBaseline، باستثناء كائنات المخطط وسجل الميجريشنات:

- الموظفون.
- الحضور والـlogs والـalerts والجزاءات.
- طلبات وأرصدة الإجازات والتصاريح.
- سجل الرواتب والفترات والمسيرات والبنود والسلف والأقساط والتعديلات.
- التنبيهات و`notification_alert_state`.
- إعدادات الشركة والـcron.
- المسيرات المعتمدة والمدفوعة والقيود المرتبطة بها.

أي فرق غير متوقع = فشل صريح.

## 8. فحوص التطبيق دون نشر

بعد نجاح قاعدة البيانات:

1. TypeScript type-check.
2. الاختبارات الموجهة لجداول العمل.
3. الاختبارات الكاملة.
4. lint.
5. مراجعة فرق الفرع كاملًا.
6. تأكيد تطابق `EmployeeProfileLegacy.tsx` مع `main`.
7. تأكيد عدم إنشاء Vercel Deployment.

لا يتم تشغيل Vercel Build أو Preview ضمن هذه المرحلة.

## 9. ما لا تعالجه V1

- لا ورديات ليلية.
- لا Split shifts.
- لا تتبع راحة.
- لا تكليف تلقائي بالعمل في عطلة رسمية.
- لا ضمان لتسليم Push بعد قبول طلب HTTP في الطابور؛ التنبيه Best-effort مع مراجعة تشغيلية.
- حضور يوم غير مقرر بلا انصراف يحتاج مراجعة بشرية قبل الراتب.

هذه حدود موثقة، وليست مبررًا لتوسيع التطوير قبل إثبات سلامة النطاق الأصلي.

## 10. الإنتاج قرار منفصل

حتى نجاح البروفة لا يجيز:

- تطبيق الميجريشنات على الإنتاج.
- إنشاء جداول حقيقية.
- فتح Feature Flag.
- إعادة حساب حضور أو راتب سابق.
- تغيير cron.
- إنشاء Preview أو Production Deployment.

الإنتاج يحتاج Drift review جديدًا، نافذة صيانة، خطة رجوع مثبتة، موظف Pilot بتاريخ مستقبلي، وموافقة مباشرة منفصلة.
